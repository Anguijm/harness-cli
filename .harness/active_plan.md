## Goal

Today the council runs at *review* time — after `active_plan.md` is committed and a PR is open. Whatever the council catches is then a CONDITIONAL or BLOCK that has to be remediated in follow-up commits. That works, but it spends inferential cycles on issues that should have been caught at *plan* time, when changing the plan costs zero implementation work.

`harness research <description>` runs the same persona panel that will eventually review the PR, but against just the feature description plus relevant past learnings. Each persona reads the description (and a small `recall`-style context window) and emits a structured "concerns / questions / things to consider" digest. The output writes a `## Research` block to `active_plan.md` (same replace-on-rerun pattern `harness map` uses for `## Repository Impact`).

The user reads the research digest, refines the plan against it, *then* implements. The result: the council at review time should have less to flag because the plan already accounts for what the same personas would have raised.

This is the "parallel research agents at plan time" idea borrowed from Cole Medin's Archon walkthrough — adapted to our existing CLI / git / PR workflow rather than rebuilt as a workflow engine. Highest-leverage Archon-inspired addition; the workflow-engine architecture itself is a category mismatch for our use case.

## Scope (what's in / what's out)

**In:**
- New command `harness research <description>`.
- Discovers the active persona set: canonical 7 (architecture, security, bugs, cost, maintainability, product, accessibility) when `harness.yml council.specialized` is unset/false; the repo's specialized set otherwise (e.g., sportsdata's data-quality / statistical-validity / etc.). Same logic `harness check` already uses to resolve the active persona set.
- Spins up parallel Gemini calls — one per persona — passing each persona's full prompt + the feature description + a small recall-context block (top N learnings/failures from `harness recall <description>`).
- Each persona returns a structured "research concerns" response in a strict format the parser validates (PERSONA / CONCERNS / OPEN_QUESTIONS / RELATED_PRIOR_LEARNINGS).
- Writes a `## Research` block to `.harness/active_plan.md`, replacing any prior block (mirrors `harness map`'s `## Repository Impact` replacement behavior). `--no-write` prints to stdout instead.
- Defaults are read-write to active_plan.md (this is its purpose); `--dry-run` flag prints the personas-and-context-window-only without making API calls.
- Cross-cutting safety from Phase E: fail-loud on missing API key, malformed response, transport error; sanitization of the recall-context block before injection; test seam.

**Out:**
- No automatic invocation by `harness plan`. Commands stay composable: user chains `recall` → `map` → `research` → write plan body → push.
- No iterative multi-turn refinement (the second Archon-inspired item; deferred to a future PR).
- No phase markers in active_plan.md (the third Archon-inspired item; deferred).
- No new persona files. Reuses the 7 canonical or the repo's specialized set; doesn't introduce a "research-specific" persona.

## Risk surface

- **Files / modules touched:** `src/commands/research.js` (new), `src/lib/personas.js` (new), `src/cli.js`, `harness.yml` (+ template), `CLAUDE.md` (+ template), `test/init.test.mjs`. No new package deps.
- **Cross-system effects:** writes to `active_plan.md`. Replace-on-rerun (no append-and-grow). User's plan body below the `## Research` block is preserved.
- **Cost:** N Gemini Pro calls per run, where N = number of active personas (4–7 typically). At Pro pricing that's ~$0.20 per research run. Cap with `--max-personas <n>` (default = all active) for repos that want a cheaper sub-panel.
- **Latency:** Pro is ~10s per call; running 7 in parallel takes ~10–15s wall-clock. Acceptable for a one-shot pre-plan moment.
- **Rollback plan:** the `## Research` block is a single contiguous section in `active_plan.md` with start/end markers; remove the block manually, or `git checkout` the file. Prior section content is replaced cleanly.

## Implementation decisions

**1. Replace-on-rerun, not append.** Same pattern `harness map` uses. Rationale: research output is regenerated when the user refines the description; appending grows `active_plan.md` with stale content. Markers (`<!-- harness-research-start -->` / `<!-- harness-research-end -->`) bracket the block so the replacer can find and overwrite cleanly even if the user has reordered the file.

**2. Per-persona system prompt = the persona file's existing content + a research-mode preamble.** The preamble explicitly tells the persona: "You are doing pre-plan research, not post-implementation review. The 'diff' is a one-paragraph feature description plus past learnings on related work. Output concerns the planner should address BEFORE writing implementation." This reuses persona scope without duplicating the long `## Scope` blocks each persona file already maintains.

**3. Recall context block bounded to ~1.5K tokens** (similar to Phase E.1's per-persona-prompt cap). Truncation strategy: top 3 recall hits, head and tail kept, middle elided.

**4. Sanitization for the recall block** — wrapped in `<UNTRUSTED_RECALL_CONTEXT>` tags using the same shared `sanitizeUntrusted` helper. Adds a third tag to `UNTRUSTED_CLOSING_TAGS` in `src/lib/sanitize.js`.

**5. Parallel orchestration with `Promise.allSettled`**, not `Promise.all`. One persona's failure should NOT abort the whole research run; we report partial results with the failed personas listed. Same fail-soft pattern recall uses for the query-embed path.

**6. Per-persona output schema (strict parse, fail-loud on malformed):**
```
PERSONA: <name>

CONCERNS:
- <one-line concern>
- <one-line concern>

OPEN_QUESTIONS:
- <one-line question for the planner>
- <one-line question for the planner>

RELATED_PRIOR_LEARNINGS:
- <pointer to a recall hit by date or signature, if relevant>
```
Matches the indexOf-based section parser shape `synthesize.js` ships, so we share that pattern.

## Steps

1. **Write `src/lib/personas.js`** — enumerate active persona files (canonical 7 from `CANONICAL_REVIEWER_PERSONAS` already in `check.js`; specialized set from `.harness/council/*.md` minus README + lead-architect when specialized=true). Load each file's content. Returns `[{name, prompt}]`. Refactors the existing canonical set out of `check.js` into the shared module.
2. **Write `src/commands/research.js`** — orchestrates the parallel persona calls, builds the recall context, parses responses, writes the `## Research` block.
3. **Add a third closing tag** (`</UNTRUSTED_RECALL_CONTEXT>`) to `UNTRUSTED_CLOSING_TAGS` in `src/lib/sanitize.js`.
4. **Register `research` in `cli.js`** with options: `--dry-run`, `--no-write`, `--max-personas <n>`, `-m/--model <name>`.
5. **Add `research:` block** to `harness.yml` template + this repo's copy with documented defaults.
6. **Add tests** to `test/init.test.mjs`:
   - Persona discovery returns canonical 7 in default mode.
   - Persona discovery returns the specialized set when `specialized: true`.
   - Dry-run prints the persona list + context preview without API calls.
   - With stub fetch, full run writes a properly-formatted `## Research` block.
   - Re-running replaces the block (doesn't append).
   - Missing API key → fail-loud.
   - One persona's stub failure → others still succeed; report lists the failure.
7. **Update `CLAUDE.md` doctrine** in the plan-first workflow section: insert `harness research` between recall and map (or as step 2.5) with explicit "review concerns before writing the plan body" guidance.
8. **Backport** to `templates/CLAUDE.md`, `templates/harness.yml`.
